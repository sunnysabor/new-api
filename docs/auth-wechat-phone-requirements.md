# 用户手机号与微信快捷登录需求澄清

## 背景

当前项目是一个 AI API 中转站，已有用户体系、账号密码登录、Session 鉴权、API Token 鉴权、2FA、Passkey、OAuth 相关能力。

本次需求只关注后端接口与存储适配，不考虑当前仓库内的前端页面改造。调用方是单独的前端项目。

## 当前系统现状

### 用户主表

用户主信息存储在 `users` 表，对应 `model.User`。

关键字段包括：

- `id`
- `username`
- `password`
- `email`
- `role`
- `status`
- `group`
- `wechat_id`
- `access_token`
- `quota`
- `used_quota`
- `last_login_at`

密码存储在 `users.password`，不是明文，注册或创建用户时通过 `common.Password2Hash()` 写入哈希，登录时通过 `common.ValidatePasswordAndHash()` 校验。

### 后台登录鉴权

Dashboard 类接口当前主要使用 Gin Session 鉴权。

登录成功后 `setupLogin()` 写入：

- `id`
- `username`
- `role`
- `status`
- `group`

受保护接口通过 `middleware.UserAuth()`、`middleware.AdminAuth()`、`middleware.RootAuth()` 校验登录态和角色权限。

### API Token 鉴权

中转 API 请求通过 `tokens` 表鉴权，不属于本次手机号/微信快捷登录的核心改造范围。

## 需求范围

### 本次纳入范围

- 后端支持用户绑定手机号。
- 后端支持手机号作为账号标识登录。
- 后端支持微信扫码后绑定当前系统用户。
- 后端支持已绑定微信的用户通过微信扫码快捷登录。
- 后端存储结构适配上述能力。
- 后端接口适配单独前端项目调用。

### 暂不纳入范围

- 当前仓库内前端页面改造。
- App 微信登录。
- 小程序登录。
- 公众号网页授权登录。
- 多微信渠道统一身份体系。
- JWT 登录体系重构。
- 替换现有 Session 鉴权体系。
- API Token 鉴权体系改造。

## 业务目标

### 手机号能力

用户可以绑定手机号，后续可以使用手机号和短信验证码登录。

手机号必须全局唯一，绑定手机号必须经过短信验证码验证。

### 微信扫码绑定

用户已经登录系统后，可以发起微信扫码绑定。

绑定成功后，系统将微信身份与当前 `users.id` 建立关系。

### 微信扫码快捷登录

用户未登录时，可以通过微信扫码快捷登录。

微信授权成功后，后端根据微信身份查找已绑定用户。

如果找到用户，则直接完成登录。

如果找不到用户，创建新账号并完成微信身份绑定，然后直接登录。

## 建议存储方案

### 最小改动方案

复用现有 `users.wechat_id` 字段存储微信身份。

新增字段：

```text
users.phone
```

建议字段定义：

```go
Phone string `json:"phone" gorm:"type:varchar(32);column:phone;uniqueIndex"`
```

微信身份存储规则：

- 优先使用微信 `unionid`。
- 如果微信没有返回 `unionid`，使用 `openid` 兜底。
- 存入现有 `users.wechat_id`。

优点：

- 改动小。
- 兼容现有 `users.wechat_id`。
- 不需要新增微信绑定表。

限制：

- 难以区分不同微信平台来源。
- 后续同时接 App、小程序、公众号、开放平台时可能不够灵活。

### 长期扩展方案

如果后续需要多微信渠道统一绑定，建议新增社交绑定表。

```text
user_social_bindings
```

建议字段：

```text
id
user_id
provider      // wechat
platform      // scan, app, mp, miniapp
openid
unionid
created_at
updated_at
```

当前需求只做微信扫码绑定和快捷登录，建议先采用最小改动方案。

## 执行约定

### 账号创建规则

手机号验证码登录创建账号时，前端会提供用户基本信息，后端保存账号信息。

微信快捷登录创建账号时，优先使用微信返回的用户基本信息。如果微信未返回可用的用户基本信息，前端需要补充用户输入基本信息的交互，后端再根据微信身份和用户基本信息创建账号。

`username` 必须全局唯一。建议规则：

- 手机号创建账号：优先使用前端传入的 `username`；如果未传，由后端生成 `phone_手机号后4位_随机串`。
- 微信创建账号：优先使用前端传入或微信返回的可用昵称生成展示名；`username` 由后端生成 `wx_随机串`。
- 后端生成 `username` 时必须检查唯一性，冲突时重新生成。

`display_name` 建议规则：

- 手机号创建账号：优先使用前端传入的展示名。
- 微信创建账号：优先使用微信昵称；没有微信昵称时使用前端传入展示名；仍没有时使用 `微信用户`。

### 初始密码规则

手机号验证码登录创建账号和微信快捷登录创建账号时，默认生成随机不可见密码并写入密码哈希。

用户后续如需账号密码登录，可通过重置密码或修改密码流程设置自己的密码。

### 新用户权益规则

通过手机号验证码登录或微信快捷登录自动创建的新账号，视为正常新用户。

创建成功后：

- 发放新用户初始额度。
- 按现有配置决定是否生成默认 API Token。
- 保持现有邀请奖励、注册赠送、日志记录等新用户创建逻辑的一致性。

### 短信验证码规则

短信供应商暂未确定，但后端实现时需要预留短信服务抽象。

建议抽象能力：

- 发送验证码。
- 校验验证码。
- 按手机号、IP、场景进行频控。
- 验证码过期时间控制。
- 防重复发送。
- 防暴力猜测。

验证码场景建议使用 `purpose` 区分：

- `bind`：绑定手机号。
- `login`：手机号验证码登录。
- `change`：换绑手机号，预留。

验证码存储建议：

- Redis 优先。
- Redis 未启用时，使用项目现有验证码/缓存能力或内存缓存兜底。
- 验证码有效期建议 5-10 分钟。

### 微信 state 规则

微信扫码绑定和快捷登录必须使用 `state` 防 CSRF 和串号。

`state` 建议存储内容：

- 场景：`bind` 或 `login`。
- 绑定场景的 `user_id`。
- 创建时间。
- 随机 nonce。

`state` 存储建议：

- Redis 优先。
- Redis 未启用时，使用 Session 或内存缓存兜底。
- 有效期建议 5-10 分钟。
- 回调消费成功后立即删除，避免重复使用。

### 安全增强规则

绑定手机号、绑定微信属于账号安全相关操作。

本次可以先复用 `UserAuth()` 保证用户已登录。

后续增强建议：

- 对绑定、解绑、换绑类操作接入现有 2FA/Passkey 安全验证。
- 对短信发送、微信登录入口接入现有频控和人机校验能力。
- 对自动创建账号增加风控日志。

## 建议后端接口

### 手机号绑定

```http
POST /api/user/phone/bind
```

鉴权：需要 `UserAuth()`。

请求示例：

```json
{
  "phone": "13800138000",
  "code": "123456"
}
```

说明：

- 如果暂不接短信验证码，可以先预留 `code` 字段。
- 绑定前需要检查手机号是否已被其他用户占用。

### 手机号解绑

```http
POST /api/user/phone/unbind
```

鉴权：需要 `UserAuth()`。

说明：

- 是否允许解绑需要业务确认。
- 如果用户只有手机号一种可用登录方式，建议禁止解绑。

### 手机号密码登录

暂不作为本次核心目标。本次手机号登录优先实现“手机号 + 短信验证码”。

### 发送手机号验证码

```http
POST /api/user/phone/code
```

鉴权：根据场景决定。

- 绑定手机号：需要登录。
- 手机号验证码登录：不需要登录，但需要频控和人机校验。

请求示例：

```json
{
  "phone": "13800138000",
  "purpose": "bind|login|change"
}
```

### 手机号验证码登录

```http
POST /api/user/phone/login
```

请求示例：

```json
{
  "phone": "13800138000",
  "code": "123456"
}
```

处理规则：

- 验证手机号验证码。
- 查询 `users.phone`。
- 用户存在且状态正常，则调用现有 `setupLogin()` 完成登录。
- 用户不存在时，前端会引导用户输入基本信息；后端根据手机号、验证码和基本信息创建新账号，绑定手机号，并调用现有 `setupLogin()` 完成登录。
- 新账号创建后发放新用户初始额度，并按现有配置决定是否生成默认 API Token。

### 微信绑定二维码地址

```http
GET /api/oauth/wechat/bind_url
```

鉴权：需要 `UserAuth()`。

作用：生成微信扫码授权地址。

后端处理：

- 生成短期 `state`。
- 将 `state -> user_id` 存入 Redis 或 Session。
- 返回微信授权 URL。

返回示例：

```json
{
  "success": true,
  "data": {
    "url": "https://open.weixin.qq.com/connect/qrconnect?..."
  }
}
```

### 微信快捷登录二维码地址

```http
GET /api/oauth/wechat/login_url
```

鉴权：不需要登录。

作用：生成微信快捷登录授权地址。

后端处理：

- 生成短期 `state`。
- 将 `state -> login` 场景存入 Redis 或 Session。
- 返回微信授权 URL。

### 微信授权回调

```http
GET /api/oauth/wechat/callback
```

鉴权：不需要登录。

微信回调参数：

```text
code
state
```

后端处理：

1. 校验 `state` 是否存在且未过期。
2. 使用 `code` 调微信接口换取 `access_token`、`openid`、`unionid`。
3. 根据 `state` 判断场景是绑定还是登录。
4. 绑定场景：
   - 根据 `state` 取出当前系统 `user_id`。
   - 检查该微信身份是否已绑定其他用户。
   - 检查当前用户是否已绑定微信。
   - 写入 `users.wechat_id`。
5. 登录场景：
   - 根据微信身份查询 `users.wechat_id`。
   - 找到用户且用户状态正常，则调用 `setupLogin()`。
   - 找不到用户，则创建新账号并绑定微信身份，然后调用 `setupLogin()`。
   - 微信快捷登录创建账号时，优先使用微信返回的用户基本信息。
   - 如果无法获取微信用户基本信息，前端需要增加用户输入基本信息的交互。
   - 新账号创建后发放新用户初始额度，并按现有配置决定是否生成默认 API Token。

## 微信绑定冲突规则

建议规则：

- 一个微信身份只能绑定一个系统用户。
- 一个系统用户默认只能绑定一个微信身份。
- 如果当前用户已绑定微信，默认不允许重复绑定。
- 如果微信身份已绑定其他用户，拒绝绑定。
- 如果用户状态为禁用，不允许快捷登录。
- 微信绑定后的解绑、换绑能力暂不实现，留作后续扩展。

## 登录态返回方式

建议保持现有 Session 机制。

微信快捷登录成功后，仍调用 `setupLogin()` 写入 Gin Session。

单独前端项目调用时需要注意：

- 前端请求需要携带 credentials。
- 后端 CORS 需要允许 credentials。
- Cookie 的 `SameSite`、`Secure`、Domain 需要适配跨域部署。

如果后续希望前后端完全分离且不依赖 Cookie，可以另行设计登录 token 或 JWT，但不建议纳入本次最小改造。

## 已确认事项

1. 手机号登录采用“手机号 + 短信验证码”。
2. 手机号必须全局唯一。
3. 绑定手机号必须短信验证。
4. 微信快捷登录找不到绑定用户时，创建账号并自动绑定微信身份。
5. 微信解绑、换绑暂不考虑，留作后期实现。
6. 微信扫码登录优先复用现有项目能力；如果现有能力不足，再新增实现。
7. 跨域问题暂不处理，记录为后续待办。
8. 手机号验证码创建账号时，前端会提供用户基本信息，后端保存账号信息。
9. 手机号验证码创建账号后发放新用户初始额度，并按现有配置决定是否生成默认 API Token。
10. 微信快捷登录创建账号后发放新用户初始额度，并按现有配置决定是否生成默认 API Token。
11. 微信扫码回调完成后返回 JSON，由前端负责跳转。
12. 微信登录优先使用 `unionid`，无 `unionid` 时允许使用 `openid` 兜底。

## 后续待办

- 独立前端项目跨域访问后端时，需要补充 Cookie、CORS、`SameSite`、`Secure` 配置方案。
- 确认短信服务供应商，以及所需配置项。
- 验证微信扫码登录是否能稳定获取微信用户基本信息；如果不能，前端需要补充用户输入基本信息的交互，后端需要提供对应创建账号能力。

## 原始待确认问题记录

1. 手机号登录是否只做“手机号 + 密码”，还是必须支持“手机号 + 短信验证码”。
2. 手机号是否必须唯一。建议唯一。
3. 绑定手机号是否必须短信验证。建议必须。
4. 微信快捷登录找不到绑定用户时，是返回“请先绑定账号”，还是自动创建用户。当前建议返回“请先绑定账号”。
5. 微信绑定后是否允许解绑或换绑。
6. 微信扫码使用开放平台网页登录能力，还是已有 `controller/wechat.go` 的现有能力已经可用。
7. 单独前端项目与后端是否同域。如果跨域，需要确认 Cookie 配置。

## 推荐实施顺序

1. 给 `users` 增加 `phone` 字段。
2. 新增短信验证码发送、校验能力。
3. 新增手机号绑定接口。
4. 新增手机号验证码登录接口，支持未注册手机号自动创建账号。
5. 新增微信绑定和快捷登录的 `state` 机制。
6. 优先复用现有微信能力，完成微信绑定和快捷登录。
7. 微信快捷登录未找到用户时，创建账号并绑定微信身份。
